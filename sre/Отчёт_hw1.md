# Отчёт: приложение «Дневник питания» (food-diary)

## 1. Доменная область приложения

Приложение — дневник питания. Пользователь ведёт дневник приёмов пищи и контролирует потребление калорий и БЖУ (белки, жиры, углеводы).

Ключевые сценарии:

- **Профиль и нормы.** Пользователь заполняет профиль (пол, возраст, рост, вес, уровень активности) и цель (снижение / поддержание / набор веса). Приложение рассчитывает персональную суточную норму калорий по формуле Миффлина—Сан Жеора с поправочным коэффициентом на активность и цель.
- **Справочник продуктов.** Продукты хранятся в собственной БД (калории и БЖУ на 100 г). Недостающий продукт можно найти в открытой базе Open Food Facts: состав подтягивается автоматически и кешируется в Redis.
- **Дневник.** Пользователь добавляет записи о приёмах пищи (продукт, вес, тип приёма, дата), приложение считает калории и БЖУ по каждой записи и по дню, сравнивает с нормой.
- **Роли.** Обычный пользователь управляет своим дневником и своими продуктами; администратор управляет общим справочником и пользователями (блокировка, роли).

## 2. Стек реализации

| Слой | Технология |
|---|---|
| Язык / рантайм | Kotlin 2.3.21, JVM 25 LTS (eclipse-temurin) |
| Backend | Spring Boot 4.0.6 (Web MVC, Data JPA/Hibernate, Security, Validation, Actuator) |
| БД | PostgreSQL 17, миграции — Flyway (V1–V6), `ddl-auto: validate` |
| Redis | Redis 7: HTTP-сессии (Spring Session) и кеш ответов внешнего API |
| Frontend | Серверный рендеринг FreeMarker (.ftlh) + Bootstrap 5 + vanilla JS (AJAX) |
| REST API | Контракт OpenAPI (`src/main/resources/openapi/openapi.yaml`), DTO генерируются openapi-generator |
| Сборка | Gradle (wrapper в репозитории), multi-stage Dockerfile, non-root пользователь |
| Запуск | docker compose (app + PostgreSQL + Redis); прод-обвязка Traefik — в `docker-compose.prod.yaml` |
| Тесты | JUnit 5, Testcontainers (реальные PostgreSQL и Redis), 79 тестов |

Взаимодействие клиент—сервер: HTTP/1.1, HTML-страницы (FreeMarker) и JSON REST API (`/api/**`) поверх одного приложения.

## 3. Основные сущности доменной области

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| `UserEntity` | Учётная запись пользователя | email, пароль (bcrypt), включённость |
| `RoleEntity` | Роль доступа | ROLE_USER, ROLE_ADMIN |
| `UserProfileEntity` | Профиль и норма КБЖУ | пол, возраст, рост, вес, уровень активности, цель |
| `GoalEntity` | Цель по весу | тип цели, поправочный коэффициент |
| `ProductEntity` | Продукт справочника | название, калории/БЖУ на 100 г, владелец, публичность |
| `FoodEntryEntity` | Запись дневника питания | пользователь, продукт, вес порции, тип приёма пищи, дата, расчётные калории/БЖУ |
| `BaseAuditableEntity` | Общая основа | даты создания/обновления (аудит) |

CRUD-операции реализованы над всеми сущностями: продукты (веб-интерфейс + `/api/products`), записи дневника (веб + `/api/diary`), профиль, цели, пользователи (админ-панель). REST-контроллеры: `ProductController`, `DiaryController`, `NutritionLookupController`; ошибки API — единый `ApiExceptionHandler`.

## 4. Соответствие методологии 12 факторов

### 1. Кодовая база — соответствует

Одно приложение — один git-репозиторий. Репозиторий деплоится в несколько контуров (локальный docker compose, прод за Traefik), то есть «одна кодовая база — много деплоев». Общих модулей с другими приложениями нет; весь код относится к одному сервису.

### 2. Зависимости — соответствует

Все зависимости объявлены явно в `build.gradle.kts` с зафиксированными версиями; версия сборочного инструмента закреплена Gradle wrapper (`gradlew` в репозитории). Неявных системных зависимостей нет: рантайм (JDK 25 LTS) поставляется контейнером `eclipse-temurin:25`, тулчейн при необходимости скачивается автоматически (foojay-resolver). Новый разработчик поднимает приложение одной командой из README (`cp .env.example .env && docker compose up`), ничего не устанавливая на хост, кроме Docker: базовый compose самодостаточен, прод-обвязка Traefik вынесена в отдельный файл-оверрайд.

### 3. Конфигурация — соответствует

Всё, что меняется между контурами, вынесено в переменные окружения: подключение к БД (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`), Redis (`REDIS_HOST`, `REDIS_PORT`), порт приложения (`SERVER_PORT`), секреты (`APP_ADMIN_EMAIL`, `APP_ADMIN_PASSWORD`), флаг внешнего провайдера (`OPEN_FOOD_FACTS_ENABLED`), кеш шаблонов (`FREEMARKER_CACHE`), публикация (`APP_PORT`, а на проде — `CONTEXT_NAME`, `DOMAIN`). Значений по умолчанию в коде для секретов нет; состав переменных задокументирован в `.env.example`. Один и тот же артефакт запускается в разных контурах без пересборки — меняется только окружение.

### 4. Сторонние сервисы — соответствует

PostgreSQL, Redis и внешний API продуктов (Open Food Facts) — подключаемые ресурсы. Адреса задаются конфигурацией (`spring.datasource.url`, `provider.open-food-facts.base-url`), приложение не различает локальный контейнер и управляемый облачный сервис: переключение выполняется заменой переменных окружения без изменения кода. Redis подключается как отдельный ресурс через `REDIS_HOST`/`REDIS_PORT`. Ответы внешнего API деградируют мягко: настроены таймауты (5 с на подключение, 10 с на чтение), сбой внешнего сервиса превращается в понятную ошибку API, а не в падение приложения.

### 5. Сборка, релиз, запуск — соответствует

Стадии разделены. Сборка: `./gradlew bootJar` собирает артефакт `fooddiary-1.0.0.jar`; multi-stage Dockerfile упаковывает артефакт в образ — сборка никогда не выполняется в работающем контуре. Релиз: неизменяемый образ `food-diary:${APP_VERSION}` (версия задаётся в `build.gradle.kts`, сейчас 1.0.0) плюс конфигурация окружения; новый релиз = новый тег образа, старые образы остаются доступными для отката. Запуск: контейнер стартует с конкретным набором env-переменных.

### 6. Процессы — соответствует

Все состояние вынесено из процесса: доменные данные (дневник, продукты, пользователи) — в PostgreSQL, HTTP-сессии аутентификации — в Redis через Spring Session (`spring-boot-starter-session-data-redis`), кеш внешнего поиска — тоже в Redis. В памяти процесса нет ни пользовательского состояния, ни сессий: процесс можно перезапустить в любой момент без потери данных, а несколько реплик работают за балансировщиком без sticky-сессий. Это проверено сквозным тестом: после логина сессия читается из Redis ключа `spring:session*`, и запрос к API с этой cookie проходит. Следствие: Redis стал обязательной зависимостью аутентификации — его доступность контролируется health-чеком, и это осознанный компромисс в пользу горизонтального масштабирования.

### 7. Привязка портов — соответствует

Приложение самодостаточно: HTTP-сервер встроен (embedded Tomcat Spring Boot), приложение не деплоится во внешний контейнер сервлетов и не обслуживается внешним веб-сервером. Порт берётся из окружения (`SERVER_PORT`); Traefik на проде лишь проксирует HTTP-трафик на порт контейнера. Взаимодействие с внешним миром — только по сети, не через локальные файлы.

### 8. Параллелизм — соответствует

Масштабирование — добавлением процессов (реплик контейнера), а не увеличением одной машины: приложение stateless (см. фактор 6), единых «главных» процессов и планировщиков в коде нет (`@Scheduled` отсутствует). Нагрузку на проде принимает Traefik, распределяя запросы по репликам.

### 9. Утилизируемость — соответствует

Старт JVM-приложения — секунды, долгого прогрева нет. Graceful shutdown настроен явно (`server.shutdown: graceful`, таймаут фазы `spring.lifecycle.timeout-per-shutdown-phase: 30s`): по SIGTERM приложение перестаёт принимать новые запросы и дозавершает запросы в полёте, что видно в логах остановки. Готовность процесса проверяется Spring Boot Actuator: `/actuator/health` (суммарное состояние, включая PostgreSQL и Redis) и пробы `/actuator/health/liveness`, `/actuator/health/readiness`; по `/actuator/health` же работает healthcheck контейнера в docker compose, поэтому нездоровый контейнер перезапускается (`restart: unless-stopped`). Контейнер работает под непривилегированным пользователем (`USER fooddiary` в Dockerfile). Внезапная остановка контейнера безопасна: состояние — во внешних хранилищах (см. фактор 6).

### 10. Паритет dev/prod — соответствует

Разработка, локальный запуск и прод используют одинаковый стек и одинаковые образы (eclipse-temurin 25, postgres:17, redis:7) и одинаковый способ запуска (docker compose). Отличие контуров — только в конфигурации (env) и внешней обвязке: на проде добавляется Traefik с TLS. Сквозной интеграционный тест поднимает реальные PostgreSQL и Redis через Testcontainers (те же версии образов, что в проде), то есть тестовое окружение совпадает с продовым по СУБД, кешу и хранилищу сессий.

### 11. Логирование — соответствует

Приложение пишет логи в stdout как поток событий (консольный аппендер Logback, используемый Spring Boot по умолчанию; файловых аппендеров и зашитых адресов лог-хранилищ в конфигурации нет). Куда логи попадают дальше — решает окружение (`docker logs`, внешний сборщик), приложение об этом не знает; смену инструмента сбора можно выполнить без изменения кода.

### 12. Административные процессы — соответствует

Миграции схемы — Flyway: применяются тем же артефактом и с тем же конфигом при старте новой версии приложения (V1–V6 в `src/main/resources/db/migration`), вручную на БД ничего не исполняется; `ddl-auto: validate` гарантирует, что схема и код не разъедутся. Создание администратора — `AdminBootstrapService`: одноразовый автоматизированный процесс с тем же кодом и конфигом (учётные данные из `APP_ADMIN_EMAIL`/`APP_ADMIN_PASSWORD`, запуск идемпотентен, без переменных просто пропускается). Разовые правки данных руками на проде не практикуются.

## Итог

Приложение соответствует всем 12 факторам. Состояние полностью вынесено из процесса: доменные данные — в PostgreSQL, HTTP-сессии — в Redis (Spring Session), конфигурация — в переменных окружения. Артефакт сборки неизменяем и версионирован, масштабирование горизонтальное (реплики без sticky-сессий), жизненный цикл процесса управляется сигналами и health-пробами Actuator. Текущий компромисс — доступность Redis критична для аутентификации; его здоровье входит в `/actuator/health` и healthcheck контейнера.
